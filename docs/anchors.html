Create · Concepts

Claims stay one interaction away from their evidence.

An anchor is the stable join between explanatory prose and a concrete span in the repository. It is what lets Fey show its work instead of presenting generated documentation as an authority.

Anchors do not make prose automatically correct. They make the supporting source explicit, inspectable, and structurally valid.

The mental model

Claim“The handler validates input first.”
Anchorsrc/api.ts#handleRequest
Source spanLines 42–68, current hash

The prose, link, and source have different jobs. The prose helps a person understand. The anchor identifies what the prose claims to explain. The source remains the final evidence when the two disagree.

Symbol anchors

The indexer emits a repository-relative file and a citable symbol. Fey derives an ID with this shape:

span ID
src/orders/service.py#OrderService.place_order

Qualify members enough to avoid collisions. A method should normally include its class or module owner. The final manifest also records line boundaries, kind, and a content hash derived from the source.

manifest span
{
  "id": "src/orders/service.py#OrderService.place_order",
  "file": "src/orders/service.py",
  "symbol": "OrderService.place_order",
  "kind": "method",
  "startLine": 24,
  "endLine": 68,
  "hash": "…"
}

Universal line-range anchors

Not every meaningful region has a discoverable symbol. Configuration, module-level setup, templates, generated glue, and unusual languages still need a way to be cited.

line-range anchor
config/routes.yaml#L14-27

The server synthesizes this span from the file when it is requested. The file and bounds must still exist. This makes every line citable without pretending that a parser found a symbol.

Honest fallback

A raw line range is better than an invented symbol. Fey prefers an explicit limitation over a more polished but unverifiable link.

How a page binds prose to anchors

A page is human-readable Markdown. A block record carries the machine-readable relationship between one marked prose claim and one or more accepted spans.

page and block contract
<!-- olo:request-validation -->
The request handler validates the payload before
passing work to the domain service.

{
  "id": "request-validation",
  "anchors": [
    "src/api.ts#handleRequest",
    "src/domain/service.ts#Service.execute"
  ],
  "origin": "ai"
}

The reducer checks that every marker has exactly one block, every block has a marker, IDs are unique, and every referenced anchor resolves. It writes nothing when one unit breaks the contract.

When one claim needs several spans

Use multiple anchors when a sentence describes a relationship—such as a route delegating to a service, a command loading configuration before execution, or an error path that crosses modules. Keep the block narrow enough that all cited spans support the same claim.

Avoid anchor dumping

Attaching ten loosely related symbols to a paragraph does not make it better supported. Split the prose until each block expresses one inspectable idea.

Locks, pins, and review memory

Locked block
Preserve the human-edited prose during regeneration. The system may refresh surrounding content, but it should not rewrite this claim.
Pinned anchor
Treat the selected anchor as intentional ground truth for the block rather than automatically moving it to a nearby span.
Verification
Record that a reviewer confirmed a claim against the current source. Verification is separate from git commits.
Page note
Keep a reviewer’s confirm or flag note beside the page so a later generation can respect known concerns.

Freshness and drift

Fey computes working-tree drift from git rather than treating a stored content hash as the whole freshness model. When changed lines overlap a claim’s anchored range, the Drift view raises that claim for review. A change elsewhere can still matter semantically, so hashes and line overlap are evidence—not a replacement for judgment.

What coverage can and cannot say

Coverage asks a narrow question: what share of indexed source lines falls inside at least one anchor? It is useful for finding files that the wiki ignores.

Coverage can tell youCoverage cannot tell you
Which indexed files have little or no explanationWhether the explanation is semantically correct
Whether a map-reduce unit missed part of its assigned file setWhether the page architecture is useful to a new reader
Whether a repository clears an agreed documentation floorWhether every important runtime path was statically discoverable

Failure behavior

Anchor failures should be explicit and leave prior valid output intact.

  • A missing file, invalid line range, duplicate ID, or malformed indexer output makes fey index fail.
  • An unknown block anchor, duplicate page ID, or marker mismatch makes fey merge fail atomically.
  • An unresolved diagram call is marked unresolved and carries no anchor rather than pointing at guessed code.
  • An un-attributed live diff hunk remains visible as such and fails the optional stop gate.

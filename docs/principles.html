Reference · Principles

Design for evidence, not for the appearance of certainty.

Fey’s product behavior, file formats, diagrams, gates, writing, and visual identity all follow the same idea: a useful explanation keeps a visible route back to what makes it true.

These principles are constraints for future features. They explain why Fey separates generative judgment from deterministic bookkeeping and why the interface looks like a working physicist’s board rather than a polished report detached from source.

Anchor before prose

Generate the evidence catalog before writing the explanation. A model is good at choosing structure, analogy, and language. It should not also invent the file, symbol, or line range that appears to support its claim.

Product consequence

Indexing is runnable and repeatable. Pages may cite only accepted IDs. The universal line-range form is available when symbol extraction cannot express the evidence honestly.

Put deterministic code at trust boundaries

Use generative reasoning where interpretation is valuable. Use ordinary code where a binary invariant can be checked.

Generative workDeterministic boundary
Choose useful wiki pagesValidate every referenced span
Describe a control flowValidate roots, parents, lanes, cycles, and anchors
Explain a working-tree changeRequire a note for every current hunk signature
Score subjective qualityRun objective commands and recompute the weighted total
Propose an improvementBind acceptance to a git-state fingerprint and exact revert

Prefer closer evidence over stronger language

A claim is not trustworthy because it sounds measured. It is more useful when the reader can inspect the cited code, the current diff, the command result, or the score history without leaving the explanation.

Fey should avoid confidence badges that summarize too much. Show the file, symbol, line range, freshness, authorship, command, or gate that produced the state.

Keep uncertainty visible

Static reading cannot resolve every call. Line overlap cannot detect every semantic dependency. Coverage cannot prove correctness. A model-authored rationale can still be wrong.

The interface should name these limits in the place where they matter:

  • Unresolved diagram calls remain dashed and unanchored.
  • Missing drift attribution says “Unattributed” and fails the optional gate.
  • Coverage is labeled as anchored-line coverage, not documentation accuracy.
  • A failed hook explains the missing outcome instead of returning success-shaped output.

Make one attributable move

The improve loop explores several directions in parallel but applies one coherent candidate at a time. This is not only a git preference. It preserves causal legibility: the score change can be attached to a specific decision.

Interaction consequence

The Optimize view shows proposals as context, one picked move as the attempt, and one keep-or-revert decision. It should not flatten a batch of unrelated edits into one green point.

Hand off reversibly

Autonomous work should arrive in a form a maintainer can inspect and decline. Improve runs happen in an isolated worktree. The default finalize path lands accepted work as uncommitted source-branch changes rather than silently merging it.

Rejection also has a strong contract: tracked files return to the previous kept state and candidate-created untracked files disappear. The rejected score remains as evidence that the direction was tried.

Keep the durable state plain

Markdown and JSON are intentionally ordinary. They can be reviewed in a pull request, edited without a proprietary client, copied between environments, and recovered when an agent session ends.

The local viewer is a projection of the bundle, not the only place where the information exists.

Write from the maintainer’s side of the screen

Fey copy should name things people recognize and control. “Start the viewer” is clearer than “initialize the visualization runtime.” “Explain this hunk” is clearer than “populate attribution metadata.”

Lead with the mechanism
State what the system does, then what that changes for the reader.
Keep nouns stable
A span, claim, hunk, proposal, gate, or iteration should keep the same name across the skill, CLI, viewer, and documentation.
Make failure actionable
Name the invalid file, missing anchor, failed command, dirty path, or next command. Do not apologize or return a vague fallback.
Do not manufacture proof
Examples must be labeled as examples. Product claims should describe behavior present in the repository.

Use a visual grammar that explains the product

The Fey identity is based on two line types from a Feynman diagram. They are not decoration; they map to the two product verbs.

Directed chalk line
Create. Source moves into an indexed explanation. Amber marks the evidence vertex where a claim meets accepted code.
Sky-blue wave
Improve. A proposal and a metric exchange information until the loop finds a higher accepted state.
Chalk sheet
Evidence. Light surfaces hold source, commands, schemas, and artifacts; the dark board holds questions and claims.
Faded chalk
Context. Secondary information recedes without disappearing.

Spend visual boldness where it teaches

The memorable interaction should be the relationship between a claim and its evidence—not generic motion around every section. Fey uses one orchestrated provenance trace in the home hero, then keeps documentation quiet: stable widths, thin rules, readable code, and restrained state color.

Motion must preserve meaning when disabled. Keyboard focus must reveal every interactive relationship that hover reveals. Mobile layouts should reorder claim and evidence vertically rather than shrinking a desktop diagram until neither can be read.

A test for future features

Before adding a feature, ask:

  1. What concrete maintainer question does this answer?
  2. What artifact or source makes the answer inspectable?
  3. Which part requires generative judgment?
  4. Which invariant can ordinary code enforce?
  5. How does failure remain explicit and recoverable?
  6. Can the durable result survive without the viewer?

If the feature cannot answer those questions, it probably adds presentation without adding explainability.
